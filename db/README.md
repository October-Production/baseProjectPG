# Что портал ожидает от базы (PostgreSQL)

Скриптов здесь нет намеренно: объекты создаёт сторона базы. Это описание контракта — что именно
вызывает приложение и в каком виде ждёт ответ.

Соглашение то же, что в BanknoteOps: все функции лежат в схеме `csen`, принимают параметры
`jsonb` и возвращают **одно значение json** — не набор строк. Поэтому в слое данных нет ни XML,
ни построителей документа из нескольких result set'ов.

Если для портала заведут отдельную схему, меняется одна константа:
`DbCore/Repositories/PgSchema.cs`.

## 1. Системный журнал

Те же две функции, что использует BanknoteOps.

| Функция | Параметры | Возвращает |
|---|---|---|
| `csen.log_event(entity, op, json, "user", err)` | `text, text, jsonb, text, boolean` | `bigint` — идентификатор строки журнала |
| `csen.log_event_end(id, json, err)` | `bigint, jsonb, boolean` | — |

- `entity` — сущность или процесс (`dictionary`, `payment_order`, `role`, `permission`);
- `op` — что делали (`list`, `item`, `save`, `delete`);
- `json` при начале операции — тело запроса как есть;
- `json` при завершении — `{"root": <тело запроса>}`, а если операция упала, рядом добавляется
  ключ `"error"` с текстом ошибки;
- `err` — признак ошибки.

Вызывает их только фоновая служба `SystemLogWriter`: запрос пользователя кладёт запись в очередь
и идёт дальше, а `log_id` между началом и концом операции хранит сама служба.

## 2. Выдача прав

| Функция | Параметры | Возвращает |
|---|---|---|
| `csen.get_user_roles(usr)` | `jsonb` | массив имён ролей |
| `csen.get_user_permissions(usr)` | `jsonb` | массив имён прав |

`usr` — пользователь целиком:

```json
{
  "name": "SENSE\\ivanov",
  "login": "ivanov",
  "domainName": "SENSE",
  "host": "(10.0.0.5)ws-ivanov.sense.bank.int",
  "fio": "Іванов І.І.",
  "mail": "ivanov@sense.bank",
  "groups": ["TreasuryPortal-Users", "TreasuryPortal-Admins"],
  "roles": [],
  "permissions": []
}
```

Решение принимается по `groups` — именам AD-групп, которые приложение уже разрешило из SID'ов.
Роли запрашиваются первыми, и в вызов `get_user_permissions` пользователь приходит уже с ними
(поле `roles` заполнено).

Ответ — массив строк `["TPReader", "TPWriter"]`; массив объектов вида `[{"name": "TPReader"}]`
тоже принимается.

Имена ролей и прав портала — в `src/TreasuryPortal.Web/Auth/AppAccess.cs`:

- роли: `TPReader`, `TPWriter`, `TPAdmin`;
- права: `TPDictionaryRead`, `TPAuditRead` (список растёт вместе с сущностями).

## 3. Справочники

| Функция | Параметры | Возвращает |
|---|---|---|
| `csen.dictionary_list(user_data, request)` | `jsonb, jsonb` | массив записей |
| `csen.dictionary_lists(user_data, request)` | `jsonb, jsonb` | объект, где ключ — имя справочника |

`request` для первой — `{"name": "currency"}`, для второй — `{"names": ["currency", "status"]}`.

Ожидаемые поля записи: `elementID`, `code`, `name`, `shortName`, `dateFrom`, `dateTo`.
Лишние поля просто попадут в ответ как есть.

## 4. Сущности

Каждая сущность обслуживается четырьмя функциями (см. `EntityRepositoryCore`):

| Назначение | Имя | Параметры |
|---|---|---|
| список | `csen.<сущность>_list(user_data, request)` | `jsonb, jsonb` |
| карточка | `csen.<сущность>_item(user_data, request)` | `jsonb, jsonb` |
| сохранение | `csen.<сущность>_save(user_data, request)` | `jsonb, jsonb` |
| удаление | `csen.<сущность>_delete(user_data, request)` | `jsonb, jsonb` |

`user_data` — тот же объект пользователя, что и выше. Он приходит **первым параметром в каждую
функцию**: по нему функция решает, что человеку видно и что ему можно, — проверка прав на стороне
приложения его не заменяет.

## 5. Соглашение об ответе и ошибках

Нормальный ответ — просто данные: массив для списка, объект для карточки.

Ошибки приходят в том же документе массивом `errors`:

```json
{
  "errors": [
    { "type": "err", "code": "limit.exceeded", "message": "Ліміт перевищено", "details": null }
  ]
}
```

**Важно.** Ответ, в котором есть и данные, и `errors`, — это частичный результат со своими
предупреждениями: приложение отдаёт данные клиенту, а ошибки показывает рядом. Настоящей
ошибкой HTTP (400) становится только ответ, в котором нет ничего, кроме `errors`.

Исключение, поднятое через `RAISE EXCEPTION` (SQLSTATE `P0001`), приложение считает
сообщением для пользователя и показывает текст из `hint` — так же, как это делает BanknoteOps.
Все остальные ошибки PostgreSQL попадают наружу коротким техническим текстом, а подробности
остаются в логе сервера.

## 6. Одновременные правки

Приложение не ставит записи в очередь и замков не держит. Две правки, в том числе одной и той же
записи, могут прийти в функции одновременно: от разных пользователей, с разных узлов IIS,
из других приложений. Замок на стороне приложения видел бы только свой процесс, поэтому его нет
намеренно — корректной при параллельном вызове должна быть каждая функция `_save` и `_delete`.

| Ситуация | Чем решается в функции |
|---|---|
| два одинаковых добавления дают дубль | уникальное ограничение, `insert … on conflict` |
| «прочитал — проверил — записал» | `select … for update` по строке, от которой зависит проверка |
| двое открыли одну запись, второй затирает правки первого | версия строки: `_item` отдаёт версию, `_save` принимает её обратно и меняет запись, только если версия та же |
| операция должна идти строго одна (закрытие дня, импорт) | `pg_advisory_xact_lock(<ключ>)` в начале функции |

Когда версия не совпала или проверка не прошла, функция поднимает `RAISE EXCEPTION` с текстом
для пользователя в `hint` (раздел 5), например «Запис змінено іншим користувачем, оновіть
сторінку». Приложение покажет этот текст как есть.
